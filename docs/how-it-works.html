It reads thousands of homelab, self-hosting, AI, and virtualization posts every week. It groups them into trends, weighs what's worth saying, and hands Rich a fresh content brief every Monday morning.

5 data streams 7 specialist roles $0 per run runs on one Mac
In one paragraph

Every Sunday at 3 AM, a small program wakes up on Rich's Mac. It scans Reddit, YouTube, Hacker News, a curated list of vendor blogs, and the latest software releases relevant to homelabbers. Then a team of specialized AI workers — each with one job — summarize what they found, find the patterns, decide which patterns matter for 2GuysTek's audience, and write a draft brief: "here are five videos we could make this week, why each one matters right now, what to title each, and what to read first." Rich opens a private webpage Monday morning, swipes through the ideas, marks the ones he wants to make, and goes to work.

Why this exists

The information firehose

In any given week, ten thousand voices in homelab / self-hosting / AI / virtualization publish, post, debate, and ship new tools. New Proxmox release. Reddit thread about a security flaw. Lawrence Systems just covered Tailscale. A vendor blog announced end-of-life for a product half your audience uses.

No human can read all of it. Even spending an hour every morning, you miss the important things and waste time on noise. So Rich built — with help — an automated research team that does the reading for him, then hands him a short, prioritized list to react to.

Steps 2 through 7 — Making sense of it

The assembly line

Once a week, the engine walks every collected post through this assembly line. Each stop is a specialized AI worker with one job.

1

Summarize each item

~10 seconds each

For every Reddit post, YouTube title, blog entry, HN story, and GitHub release: an AI worker reads it and writes a one-sentence summary + a few key points + topic tags + a sentiment score (positive / neutral / negative) + a freshness score (is this brand new, or has the internet been debating it for years).

2

Group related items into trends

math, not magic

Many summaries are about the same underlying story. A Proxmox kernel bug shows up in a Reddit thread, a Lawrence Systems video, a Phoronix article, and a forum post. The engine measures the similarity between all 377 summaries and clusters the related ones into trends. The Proxmox kernel cluster gets stronger as more sources mention it — that's signal that it's worth talking about.

3

Pick the hottest, most diverse trends

heat × novelty × recency

From dozens of trends, pick the most worth covering. Hotness = how many sources are talking about it, how new the story is, and how recently it broke. And it enforces topic diversity: it won't hand back five AI ideas in a row. One from homelab, one from security, one from virtualization, one from AI, one from networking. Audience gets variety.

4

Turn trends into actual video ideas

the strategist

For each chosen trend, the strategist AI writes a sharp video angle — not "Top 10 Proxmox Tips" but "Why I downgraded Proxmox's kernel after Tailscale broke — and why you might need to too". It explains why now, estimates audience fit, drafts 3–5 candidate titles, sketches thumbnail ideas, and flags any divisive risks (AI topics and Proxmox criticism both get auto-tagged because the audience is opinionated about both).

5

Draft a script outline + sources to verify

the outline writer

For the top three ideas, a second AI drafts an actual outline: a cold-open hook, five to seven sections with timing estimates, beat-by-beat talking points, B-roll suggestions, a closing call-to-action, and — crucially — a list of links Rich should read or watch before writing the script, plus an "open questions" list of things to verify. The outline writer is trained on Rich's own past scripts so the voice and rhythm sound like him.

6

Score the titles & verify every citation

the fact checker

Each candidate title gets scored 0-100 on click-worthiness based on what's worked for 2GT before. A separate worker then double-checks every URL the outline recommends as a source — if a link wasn't in the original signals (i.e. the AI made it up), it gets flagged as "unverified, check before quoting." This catches AI hallucination before it ever reaches a script.

7

Render a beautiful brief

delivered

Everything gets stitched into a polished web page Rich opens on Monday morning. Five ideas, each with the angle, why now, ranked titles, thumbnail concepts, cross-post copy for Instagram/LinkedIn/Discord, a full outline for the top three, and the sources to read. Total time from "wake up at 3 AM" to "brief ready": about 10 minutes.

An important point

This doesn't write videos. It does the homework.

The engine never makes scripts. It never makes thumbnails. It never publishes anything.

What it does is read everything Rich would want to read if he had unlimited time, find the threads worth pulling on, and hand him a starting point. Every angle, title, outline, and source is a draft — Rich rewrites, rearranges, kills, or replaces anything that doesn't fit.

Think of it less like an AI ghostwriter and more like having a research team that works overnight: you get a stack of folders Monday morning, each with a topic, why it matters, and the homework already done. You're still the one on camera. You're still the one whose taste matters.

Critically, every AI-generated citation gets a verification flag. If the engine made something up, you see "⚠ unverified" before you read it. No surprise hallucinations.

Model routing

Five tiers, one philosophy

Use the smallest model that can do the job, escalate on low confidence or schema-validation failure. Embedding is its own dedicated model. All running locally on Apple Silicon via Ollama (Metal backend).

Tier Model Params Quant Disk Used for
embed nomic-embed-text 137M F16 274 MB summary → vector for cluster dedupe
fast gemma4:e2b ~2B effective Q4_K_M ~2 GB cluster labels, triage classification
mid gemma4:e4b ~8B Q4_K_M 9.6 GB per-signal structured summarization
heavy qwen3:30b-a3b-instruct-2507 30B MoE (3B active) Q8_0 33 GB idea + outline synthesis (JSON mode)
polish qwen3:30b-a3b-instruct-2507 30B MoE (3B active) Q8_0 (shared) unconstrained prose rewrite
Why MoE for heavy
Qwen 3 30B-A3B is a 30B-parameter mixture-of-experts model with ~3B active per token. Inference cost scales with active params, so it runs roughly as fast as a 3B dense model on Apple Silicon while keeping 30B-class reasoning quality. Replaced dense Gemma 4 31B Q8 after a single Q8 call took 540 s vs 10 s on the MoE.
Why a separate polish tier
Structured-output (Ollama format=schema) calls bake JSON tokens into every decoding step, which the smaller Q4 models do well enough but produce occasional artifacts (doubled words, leaked syntax). The polish pass re-runs the prose-only fields in unconstrained mode — Q8 MoE, free-form generation — and merges back into the schema.

Vidiq path

If COMPOSIO_API_KEY is set and vidiq is connected, calls VIDIQ_SCORE_TITLE per title. 5 credits/call. Real CTR scoring against YouTube's ranker history.

Heuristic fallback

Deterministic 0-100 score from regex levers, calibrated to 2GT's actual breakouts:

  • + length sweet spot 35-65
  • + numbers, year tags, parens
  • + "vs" / comparison framing
  • + contrarian verbs (stop, killed, broke, ditched)

  • − "ultimate guide" / "how to" / clickbait phrases
Output

Each idea's title_scores gets populated with [{title, score, source}] sorted desc. The report template highlights the top 2 in emerald. Source tag is preserved so we can tell vidiq scores from heuristic at a glance.

verify_citations

deterministic · no LLM
synthesizers/citation_verifier.py
Why it exists

LLMs hallucinate plausible-looking URLs. In early runs the outline writer cited github.com/2GuysTek/<made-up-repo>. Untrustworthy citations corrode the value of the whole brief.

Logic
  • 1. Normalize URL (lowercase host, strip trailing slash)
  • 2. Build allowlist = source_signal URLs ∪ small infra-docs whitelist (proxmox.com, github.com, kubernetes.io, …)
  • 3. For each ResearchSource, set verified = url ∈ allowlist
Surface

Unverified sources render with amber border + "⚠ unverified" pill + "verify before quoting" note in the report. Per-cycle hallucination rate is logged to agent_runs for trend tracking (currently averaging ~8-14%).

The harness

How an agent call actually works

All five LLM-backed agents share a single entry point: run_agent() in ollama_client.py. The function is the enforcement layer — it owns structured output, validation, escalation, retry, and observability.

run_agent flow
  1. 1Render prompt. Load versioned template from prompts/ (no Jinja in prompts on purpose — grep-friendly). Substitute {{var}}.
  2. 2Call Ollama with the schema. POST to /api/chat with format = SchemaCls.model_json_schema(). Ollama constrains decoding to produce valid JSON conforming to that schema.
  3. 3Validate. Pydantic .model_validate_json(). Catch ValidationError + json.JSONDecodeError.
  4. 4Check confidence. Extract parsed.confidence. If < confidence_retry_below (0.55) and a stronger tier exists, escalate.
  5. 5Log to agent_runs. input_hash, output JSON, confidence, elapsed_ms, escalated_from, error.
  6. 6Return. (parsed_or_None, AgentResult) tuple. Caller decides whether to persist.
Escalation order
fast → mid → heavy

Triggered by either schema-validation failure or low confidence. The harness remembers escalated_from so we can see downstream which tier originally tried and failed.

Retry on transient errors

tenacity decorator on the underlying httpx call: 3 attempts, exponential backoff 1-8s, retries on httpx.HTTPError and OllamaError only (not on schema failures — those go through escalation instead).

HTTP timeout

900 s per call. Q8 unconstrained generation on dense models can take 5-9 min for a long outline; this is generous so we never lose work on a slow inference.

Env normalization

OLLAMA_HOST is normalized at startup — bare host:port gets http:// prepended, bind addresses (0.0.0.0, ::) get rewritten to localhost. Caught a real bug where Ollama's daemon plist set bare host:port for LAN binding.

The clustering

From 377 summaries to a handful of trends

Clustering happens entirely in Python — no LLM is involved in the math. The LLM only names the resulting clusters.

Steps
  1. 1. Embed. nomic-embed-text via Ollama /api/embed. Input is "{one_line} :: {' / '.join(key_points)}".
  2. 2. L2-normalize each vector for cosine distance.
  3. 3. Agglomerative cluster (sklearn): metric=cosine, linkage=average, distance_threshold=0.30.
  4. 4. Per cluster: top-3 dominant topics from member topic counts; mean sentiment in [-1, 1]; mean novelty.
  5. 5. Heat score from formula opposite.
  6. 6. Label via the cluster_label agent (fast tier) and persist to the clusters table.
Heat score formula
recency = 1 / (1 + avg_age_hours / 48)
heat = n_signals × (0.4 + 0.6 × avg_novelty) × recency

Volume is the dominant factor (linear scaling). Novelty has a floor (0.4) so even a cluster about an old topic gets some weight if it's spiking in volume — but a novel topic gets nearly 2× the multiplier of a stale one. Recency decays with a ~2-day half-life so a Reddit thread from 6 days ago competes fairly against one from this morning.

Topic-diversification gate is applied after heat ranking — see _select_diverse_clusters() in synthesizers/ideas.py.
Data layer

8 tables, SQLite + WAL

One file at data/engine.db. Schema lives in db.py — grep-friendly, easy to evolve. WAL mode so the GUI process can read while the pipeline writes.

Table Holds Written by Notable indexes / constraints

Why SQLite, not Postgres
Single-user local app. SQLite + WAL gives concurrent read/write with zero setup, zero daemon, zero cloud bill. The whole DB is portable as one file. If the engine ever moves to a real server, the schema in db.py is straightforward Postgres-compatible SQL.
Why also LanceDB
Reserved for vector dedupe of past ideas (planned). Idea embeddings will be persisted so the synthesizer can do a similarity search before pitching anything — if a candidate is within ε of a 90-day-old idea, surface "you've already pitched this" unless there's a significant new event tied to it.

Scheduling

macOS LaunchAgent at ~/Library/LaunchAgents/com.2gt.contentengine.weekly.plist. Sunday 3am. A second LaunchAgent keeps the FastAPI GUI process running with crash-restart (KeepAlive + 10s throttle).

Ad-hoc runs

POST /run from the GUI forks a detached subprocess via subprocess.Popen(start_new_session=True). Lock file at data/runs/.manual_run.lock tracks the PID. Zombie detection in _process_alive() via ps -p <pid> -o state=.

Eval

engine eval runs every JSON case in tests/golden/<agent>/ against the registered agent and checks the output against expectations (min_confidence, must_include_topics, sentiment_in, keyword presence). Catches model-swap regressions.

Observability via agent_runs

Every single LLM call writes a row to agent_runs. The report template reads from it to render the per-cycle "agent telemetry" table. Queries you can run by hand for forensics: 

-- Which agent is slowest on the last cycle?
SELECT agent, model_tier, AVG(elapsed_ms) ms, COUNT(*) n
FROM agent_runs WHERE cycle_id = (SELECT id FROM cycles ORDER BY started_at DESC LIMIT 1)
GROUP BY agent, model_tier ORDER BY ms DESC;

-- Where are escalations happening?
SELECT agent, escalated_from, model_tier, COUNT(*) n
FROM agent_runs WHERE escalated_from IS NOT NULL GROUP BY 1,2,3;

-- Hallucination rate trend over the last 8 cycles
SELECT cycle_id, json_extract(output_json,'$.hallucination_rate') rate
FROM agent_runs WHERE agent='verify_citations' ORDER BY id DESC LIMIT 8;

Composio wrapper trick

collectors/composio_client.py indexes connected accounts by toolkit name on initialization. When execute(slug, ...) is called, it derives the toolkit from the slug prefix (e.g. YOUTUBE_LIST_CHANNEL_VIDEOS → youtube) and auto-attaches the right connected_account. Composio v3's SDK doesn't do this auto-resolution, and calls fail with InvalidParams: connected_account cannot be None without it. A Noop fallback class is returned when COMPOSIO_API_KEY is unset so the engine still runs end-to-end (just without OAuth'd sources).

Cost model

Why this costs $0 per run

A typical weekly cycle makes ~120 LLM calls. At GPT-4o pricing, that's roughly $0.50-$1.50 per cycle depending on context size — $25-75/year for the engine to run on its own.

Running locally on the M5 Max, the same 120 calls cost zero dollars (the hardware was bought regardless, electricity for the ~10 min of inference is rounding error). Over the project's lifetime that's a meaningful number — and more importantly, every editorial decision the engine makes stays on this Mac.
